# MCP-сервер для интернет-магазина (shop.db): read-only доступ к данным

**Статус:** реализовано и закоммичено в `master`. `npm test` → **206/206 passed**.
Ветка разработки: `feat/shop-db-mcp-server`, слита в `master`.
Пофазный статус со ссылками на код — [homework.md](homework.md).

## Problem Statement

AI-агенту нужно отвечать на аналитические вопросы по готовой SQLite-базе интернет-магазина
(`customers` → `orders` → `order_items` → `products`). Сегодня у агента нет способа читать
базу: он не видит схему, не может выполнить SQL и не знает, где в данных ловушки — какие
статусы заказов считать, какая колонка означает «когда произошла продажа», чего в данных
просто нет. Нужен MCP-сервер, который подключается к базе через stdio и даёт агенту
безопасный read-only доступ с описаниями tools, которые кодируют и доменные правила, и
границы данных.

Отдельное требование задания: агент не должен иметь возможности изменить базу — ни через
tool, ни через SQL, ни через обход экранированием.

## Solution

Node.js MCP-сервер (ESM, `node >= 20`) через stdio, открывающий `shop.db` в режиме
`readonly`. Дизайн **гибридный**: три схемо-независимых tool'а покрывают произвольные
вопросы, три специализированных отвечают на частые аналитические запросы одним вызовом и
регистрируются только там, где схема их поддерживает.

Read-only обеспечивается не одним механизмом, а несколькими независимыми слоями (открытие
базы, лексический SQL-guard, вердикт самого движка, отсутствие write-tools), и каждый из
них измерен тестом отдельно — на том, что пропускают остальные.

Ошибки типизированы шестью кодами, санитизированы (ни путей, ни stack frame'ов) и написаны
так, чтобы агент мог исправить запрос: `no such column` дополняется списком реальных
колонок, отказ на запись — эквивалентным `SELECT`.

Путь к базе — `SHOP_DB_PATH`; при его отсутствии база ищется относительно **корня проекта**
(через `import.meta.url`, никогда через `process.cwd()`, потому что MCP-клиент запускает
сервер из произвольного каталога).

## User Stories

**Знакомство со схемой**

- Как AI-агент, я хочу увидеть список всех таблиц и представлений с числом строк и сводкой
  колонок, чтобы за один дешёвый вызов понять, что вообще есть в базе.
- Как AI-агент, я хочу получить полное описание таблицы — колонки с типами, NOT NULL, PK и
  default, foreign keys, CHECK-констрейнты, индексы, DDL и три примера строк, — чтобы
  строить корректные запросы и находить путь join'а без перебора.
- Как AI-агент, я хочу, чтобы описание примеров строк честно говорило, что это **первые три
  строки в порядке хранения, а не репрезентативная выборка**, чтобы я не делал по ним
  выводов о покрытии данных (три строки за 2026 не означают, что 2025 в таблице нет).
- Как AI-агент, я хочу при обращении к несуществующей таблице получить список реально
  существующих таблиц, чтобы исправиться за один ход, а не угадывать.

**Аналитика**

- Как AI-агент, я хочу выполнить произвольный read-only `SELECT` / `WITH…SELECT` / `VALUES`,
  чтобы отвечать на вопросы, под которые нет специализированного tool'а.
- Как AI-агент, я хочу получать `{columns, rows, row_count, limit, offset, has_more, notes}`,
  чтобы понимать, обрезан ли результат, и знать точный следующий вызов.
- Как AI-агент, я хочу получить топ клиентов по потраченной сумме вместе с числом их
  заказов, чтобы ответить на «кто потратил больше всех» одним вызовом вместо join'а трёх
  таблиц.
- Как AI-агент, я хочу получить топ товаров, где на **каждой** строке есть и units, и
  revenue, чтобы увидеть, что «best-selling» неоднозначно, и назвать в ответе выбранное
  прочтение.
- Как AI-агент, я хочу получить выручку по дням / месяцам / годам с числом заказов и
  позиций, чтобы отвечать на вопросы о периодах и трендах.
- Как AI-агент, я хочу при пустом диапазоне получать не ошибку и не пустоту, а **реальные
  границы данных** в том же формате, который принимают параметры, чтобы за один ход
  ответить «за этот период заказов нет, данные покрывают такой-то диапазон».
- Как AI-агент, я хочу управлять учётом отменённых заказов явным параметром
  (`include_cancelled`, по умолчанию `false`), чтобы решение о базе расчёта принимал я и
  проговаривал его в ответе, а не сервер молча.

**Безопасность**

- Как проверяющий, я хочу, чтобы запрос «Delete all cancelled orders» не мог изменить базу
  ни при каком способе формулировки — ни через tool, ни через SQL, ни через комментарий,
  строковый литерал, CTE, `PRAGMA`, `ATTACH` или `RETURNING`.
- Как проверяющий, я хочу, чтобы после полного прогона атакующих запросов **SHA-256 и размер
  файла базы не изменились**, чтобы гарантия read-only была измерена, а не заявлена.
- Как AI-агент, я хочу, чтобы отказ на запись содержал эквивалентный read-only запрос, чтобы
  я мог сразу предложить пользователю осмысленную альтернативу.
- Как AI-агент, я хочу, чтобы легитимные запросы вида `WHERE name = 'DROP TABLE orders'` **не**
  блокировались, потому что сервер, отвергающий всё, тоже проходит тест из одних отказов.

**Ошибки и эксплуатация**

- Как AI-агент, я хочу короткое типизированное сообщение об ошибке, а не stack trace.
- Как AI-агент, я хочу, чтобы внутренний баг сервера приходил как `INTERNAL_ERROR`, а не как
  `SQL_ERROR`, чтобы не переписывать бесконечно свой корректный запрос.
- Как разработчик, я хочу, чтобы абсолютные пути не утекали агенту ни в ошибках, ни в
  примечаниях.
- Как разработчик, я хочу, чтобы при недоступной базе сервер **не падал**, а проходил
  handshake и отвечал `CONFIGURATION_ERROR` с именем настройки, которую надо починить, —
  «SHOP_DB_PATH указывает в никуда» полезнее, чем «server failed to start».
- Как разработчик, я хочу, чтобы `stdout` был защищён от постороннего вывода, потому что
  один случайный `console.log` ломает JSON-RPC кадр и сервер выглядит мёртвым.
- Как проверяющий, я хочу README с цепочкой install → configure → run → connect и готовый
  пример конфигурации, чтобы подключить сервер, не читая код.
- Как проверяющий, я хочу, чтобы пример конфигурации был покрыт тестом, который реально его
  запускает, чтобы документация не протухла молча.

## Implementation Decisions

**Runtime.** Node.js (ESM, `node >= 20`), официальный MCP SDK
`@modelcontextprotocol/sdk@^1.30.0`, stdio transport, SQLite через `better-sqlite3`,
валидация входа через `zod`.

**Структура.** `src/`: `index.js` (entry, instructions, boot), `config.js` (резолв пути),
`db.js` (открытие базы, `runQuery`, пагинация, коэрсинг значений, дедлайн),
`sql-guard.js` (лексер + правила read-only), `introspect.js` (`list_tables`,
`describe_table`, обогащение SQL-ошибок), `analytics.js` (специализированные tools +
`probeCapabilities`), `errors.js` (коды, санитайзер, `toToolResult`), `tools.js`
(регистрация и descriptions).

**Набор tools — 6, гибридно:**

| Tool | Назначение | Лимиты |
|---|---|---|
| `list_tables` | таблицы и представления, число строк, сводка колонок | без параметров; служебные таблицы SQLite скрыты; представления не считаются |
| `describe_table(table_name)` | колонки, FK, CHECK, индексы, DDL, 3 примера строк | один объект за вызов; представления не сэмплируются |
| `run_sql_query(sql, limit?, offset?)` | один read-only `SELECT` / `WITH…SELECT` / `VALUES` | limit 100 по умолчанию, максимум 1000; ответ ≈256 KB; ячейка 4096 символов; дедлайн 5 с |
| `top_customers_by_spend(limit?, include_cancelled?)` | клиенты по сумме покупок + число заказов | limit 10 по умолчанию, максимум 100 |
| `top_products_by_sales(limit?, rank_by?, include_cancelled?)` | товары: units **и** revenue на каждой строке | limit 10 / 100; `rank_by` выбирает только порядок |
| `revenue_by_period(group_by, start_date?, end_date?, include_cancelled?)` | выручка по дням/месяцам/годам + `available_range` | даты строго `YYYY-MM-DD` |

**Почему generic SQL-tool есть.** Это главное расхождение с чисто специализированным
подходом: восемь вопросов задания закрываются набором из шести tools только потому, что
`run_sql_query` покрывает всё остальное (например, «топ-3 категории по выручке» — это
join `orders → order_items → products`, под который отдельного tool'а нет). Цена решения —
что read-only приходится защищать всерьёз, и это сделано отдельным слоем.

**Read-only — четыре независимых слоя, каждый измерен на том, что пропускают остальные:**

- **L0.** Write-tools отсутствуют в API.
- **L1.** База открывается `readonly`; сразу после открытия делается проба `sqlite_master`,
  потому что `better-sqlite3` откладывает проверку заголовка — иначе `.sql`-дамп, CSV или
  LFS-указатель открылись бы молча и упали бы только на первом запросе.
- **L2.** `db.prepare` (никогда `db.exec`: prepare принимает ровно один стейтмент) и отказ,
  если `stmt.readonly !== true`.
- **L3.** `sql-guard.js` — **лексер, а не регулярка**. Комментарии (`--`, `/* */`),
  строковые литералы и кавычки идентификаторов вырезаются **до** матчинга глаголов, поэтому
  `/* SELECT */ DELETE …` не проходит, а `WHERE name = 'DROP TABLE orders'` проходит.
  Allow-list открывающих ключевых слов (`SELECT`, `WITH`, `VALUES`), правило «ровно один
  стейтмент», denylist глаголов по всему стейтменту (ловит записи внутри CTE).

  L3 существует потому, что L1–L2 **измеренно недостаточны**: на readonly-соединении
  `ATTACH DATABASE '<существующий .db>'` выполняется успешно и позволяет читать чужую базу,
  а `PRAGMA writable_schema = ON` тоже проходит — для обоих `stmt.readonly` возвращает
  `true`. `load_extension` — там же. Это зафиксировано тестами, которые перемеряют факт, а
  не повторяют утверждение.

**Пагинация без переписывания SQL агента.** `limit`/`offset` применяются итерацией
`stmt.iterate()` с добором одной лишней строки, чтобы `has_more` был точным. Дописывание
`LIMIT n OFFSET m` к чужому SQL отвергнуто: оно конфликтует с уже написанным `LIMIT`,
меняет смысл compound-SELECT и ставит склейку строк вплотную к границе безопасности.

**Сериализация.** BLOB → `<BLOB n bytes>`, BigInt → число или строка (иначе
`JSON.stringify` уронил бы **весь** вызов из-за одной ячейки), NULL/REAL/TEXT как есть,
обрезка ячейки > 4 KB с маркером, общий потолок ответа ≈256 KB (потому что 1000 строк ×
широкий `SELECT *` — это десятки мегабайт на синхронном stdio-сервере).

**Специализированные tools регистрируются условно.** `probeCapabilities` проверяет наличие
всех колонок, которые хардкодит их SQL; если проверяющий подставит другую `shop.db`, эти
три tool'а просто отсутствуют, а агент падает обратно на `run_sql_query`. Специализированный
tool, падающий на чужой схеме, строго хуже отсутствующего.

**Доменные правила:**

- **Отменённые заказы.** Единственный статус, который фильтруется, — `cancelled`, и он
  выключаемый: `include_cancelled` по умолчанию `false`, а каждый ответ несёт `note` о том,
  на какой базе он посчитан. `new` / `processing` / `shipped` / `completed` учитываются все —
  сервер не решает за агента, считать ли ещё не отгруженный заказ выручкой.
- **Источник сумм.** Везде `SUM(order_items.quantity * order_items.unit_price)` —
  фактическая цена продажи, а не текущий `products.price`. `orders.total_amount` не
  используется как источник агрегатов.
- **Дата продажи.** Бакеты режутся по `orders.order_date`; `customers.created_at` и
  `products.created_at` — даты регистрации и отвечают на другой вопрос (об этом сказано в
  description).
- **Страна.** В базе есть настоящая колонка `customers.country` (добавлена скриптом
  сидирования, см. ниже) — вывод страны из телефонного префикса не требуется.
- **Пустой диапазон — это ответ, а не ошибка.** `revenue_by_period` возвращает пустой список
  бакетов, `available_range` с реальными границами данных и `note` с объяснением, чтобы
  агент сказал «ноль, и вот почему» за один ход.
- **Валидация дат.** Принимается только дата, с которой SQLite согласен: `'2026-13-01'`
  дал бы уверенный ноль (сравнение строк, ничего не падает), а `'2026-02-30'` молча
  сдвинулся бы на `'2026-03-02'`. Проверка «`date(?)` вернул ровно то, что передали»
  отсекает оба случая.

**Ошибки — шесть кодов:** `READ_ONLY_VIOLATION`, `SQL_ERROR`, `INVALID_ARGUMENT`,
`QUERY_TIMEOUT`, `CONFIGURATION_ERROR`, `INTERNAL_ERROR`. Неизвестная ошибка становится
`INTERNAL_ERROR`, а не `SQL_ERROR`: иначе внутренний баг сообщал бы агенту, что неверен его
запрос. Санитайзер вырезает абсолютные пути и stack frame'ы на **всех** путях к агенту,
включая `note` внутри результата интроспекции. Обогащение: `no such column` → список
реальных колонок, `no such table` → список реальных таблиц, отказ на запись → эквивалентный
`SELECT`.

**Descriptions в едином формате `WHEN TO USE / RETURNS / LIMITS`** (блок `WHAT TO PASS`
добавлен только у `run_sql_query`, где агент передаёт произвольный SQL); единообразие
проверяется структурным тестом, а не на глаз. На каждом tool'е аннотации
`readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`,
`openWorldHint: false`. У сервера есть `instructions`: сначала осмотреться, проверять
существование колонки до запроса, не выдумывать недостающее — «назвать пробел в данных —
это правильный ответ».

**Ловушка даты вынесена в description.** `order_date` объявлена `DATETIME`, то есть имеет
NUMERIC affinity: `WHERE order_date < '2026'` молча не матчит **ничего**. Description
`run_sql_query` требует полную дату или обёртку `date()` / `strftime()`.

**stdout защищён первым же стейтментом** `index.js`: `log`, `info`, `debug`, `dir`, `table`
переведены на `console.error`, потому что одна посторонняя запись в stdout ломает кадр
JSON-RPC.

**Деградация вместо падения.** Если база не открылась, сервер **всё равно** стартует,
проходит handshake, а каждый tool отвечает `CONFIGURATION_ERROR` с именем настройки;
подробность уходит в stderr оператору.

**Данные.** Исходная база: 150 клиентов, 50 товаров, 750 заказов, 1900 позиций, без колонки
`country` и без заказов 2025 года — то есть вопросы 2, 3 и 7 задания на ней честно
отвечались «в данных этого нет». Владелец решил дополнить данные: сейчас **235 клиентов,
50 товаров, 960 заказов, 2429 позиций**. Дополнение сделано одним детерминированным скриптом
с фиксированным seed'ом ([scripts/seed-extended-data.mjs](scripts/seed-extended-data.mjs),
`npm run seed`), проверяющим 14 инвариантов на каждом прогоне; ни одна исходная строка не
изменена. В README есть таблица «какие строки предоставлены, а какие сгенерированы».
У сгенерированных клиентов имя, телефонный код, домен почты и `country` согласованы между
собой.

**Docker.** Multi-stage `node:22-slim` (обе стадии на одном базовом образе ради
ABI-совместимости нативного бинарника `better-sqlite3`), `npm ci` с локфайлом, `USER node`,
exec-form `ENTRYPOINT`, база запечена в `/shop.db` и переопределяется монтированием.
Запускать **только** `docker run -i`, никогда `-it`: TTY включает эхо и портит кадры
(проверено воспроизведением порчи, а не заявлено).

**Поставка.** `README.md` (810 строк: установка, конфигурация, запуск, подключение, все
tools, гарантии read-only, происхождение данных, известные ограничения данных и техники,
ответы на все восемь вопросов), `mcp.config.example.json` (обобщённый пример), `.mcp.json`
(готовый конфиг для Claude Code), `shop.db` в репозитории, `homework.md` (пофазный статус со
ссылками на код), `tasks/plan.md` и `tasks/todo.md` (план и разбиение на 15 задач).

## Testing Decisions

**Что такое хороший тест здесь:** внешнее поведение через живого MCP-клиента поверх
дочернего процесса — вход → JSON-ответ или сообщение об ошибке. Внутренняя структура модулей
не тестируется.

**Фреймворк:** встроенный `node --test`, без внешних зависимостей. **18 файлов, 206 тестов,
все проходят.**

**Два seam:**

- **E2E через stdio** (`test/*.e2e.test.js`) — реальный `StdioClientTransport` к
  порождённому `src/index.js`: handshake, `listTools`, `callTool`. Здесь проверяются
  descriptions, отказы, конфигурационная деградация и capstone-безопасность.
- **Unit** (`test/*.test.js`) — чистые функции: лексер guard'а, резолв пути, коэрсинг
  значений, санитайзер, аналитические запросы против реальной базы.

**Покрытие:**

- **Safety capstone** ([test/safety.e2e.test.js](test/safety.e2e.test.js)): база копируется
  во временный каталог, через живого клиента прогоняются **45 атакующих запросов + 2
  инъекции идентификатора**, после чего проверяется, что **SHA-256 и размер копии не
  изменились**, `sqlite_temp_master` пуст, а `ATTACH` существующей соседней базы отклонён и
  её строки не разрешаются. Сверх очевидного списка покрыты: невложенность блочных
  комментариев (`/* /* */ DELETE … */` SQLite читает как `DELETE`), незакрытые токены,
  нулевой байт, `load_extension`, `ANALYZE`, BOM, blob-литералы, лимит длины, `pragma_*` как
  table-valued функции и три формы `RETURNING`.
- **Проверка на ложные срабатывания:** 9 легитимных запросов обязаны проходить — набор из
  одних отказов прошёл бы и на сервере, отвергающем всё.
- **Слои по отдельности:** тест с заглушкой, у которой `stmt.readonly === false`, отклоняет
  запрос, хотя guard пропустил, — L2 измерен независимо от L3.
- **Эталонные значения:** все восемь вопросов задания зафиксированы числами против
  закоммиченной базы, на обеих базах расчёта (с отменёнными и без).
- **Инварианты данных** ([test/data-invariants.test.js](test/data-invariants.test.js)):
  повторный прогон всех инвариантов по закоммиченной базе плюс две защиты самого скрипта

- **Утечки:** ни одно сообщение об ошибке во всём наборе не содержит `/`-путь или фрейм `at `.

## Out of Scope

- HTTP-транспорт — только stdio.
- Write-операции любого вида и миграции схемы: база поставляется как есть.
- Поддержка других СУБД — только SQLite.
- UI / веб-интерфейс, аутентификация, многопользовательность, кэширование.
- Worker-thread для отмены запросов — прямое следствие ограничения ниже, признано остаточным
  риском осознанно.
- Ограничение пиковой памяти внутри процесса: `SELECT randomblob(200000000)` — легитимное
  чтение, лимиты обрезают то, что **уходит** агенту, но SQLite успевает выделить память до
  этого.

## Further Notes

**Честно названные ограничения** (все выписаны в README в разделах «Known data limitations»
и «Known technical limitations»):

- **Дедлайн запроса прерывает только потоковые планы.** Проверка идёт между строками,
  поэтому она бессильна против плана, который считает весь результат до первой строки:
  голый `COUNT(*)`/`SUM` по большому join'у, `ORDER BY`, `GROUP BY`, `DISTINCT`, `UNION`.
  `better-sqlite3` не предоставляет ни interrupt, ни progress handler (проверено: их нет на
  прототипе `Database`), поэтому отменить выполняющийся стейтмент в процессе нельзя.
  Description tool'а поэтому говорит «фильтруй до join'а», а не «есть таймаут».
- **Один барьер в capstone — случайность, а не слой.** Даже с отключённым guard'ом
  эксфильтрация через `ATTACH` сегодня падает — но не потому, что её кто-то охраняет:
  `runQuery` доходит до стейтмента только через `columns()`/`iterate()`, а
  `better-sqlite3` бросает на обоих для стейтмента, не возвращающего строк. Это свойство
  кода пагинации, оно исчезнет при добавлении `.run()`-пути и никогда не покрывало
  `DELETE … RETURNING`. Capstone специально хранит ассерты про `ATTACH` и
  `sqlite_temp_master` как регрессию именно на этот случай.
- **Гео только на уровне страны**, «best-selling» неоднозначно и два прочтения называют
  **разные** товары, отменённые заказы меняют и суммы, и ранжирование — всё это вынесено в
  descriptions, чтобы агент проговаривал базу расчёта в ответе.

**Расхождения с чисто специализированным дизайном** (если сравнивать с вариантом
«specialized-only, без generic SQL»):

| | Тот подход | Наш |
|---|---|---|
| Runtime | Python + stdlib `sqlite3` | Node.js + `better-sqlite3` |
| Generic SQL-tool | сознательно нет | есть (`run_sql_query`) + лексический guard как отдельный слой |
| Число tools | ~8 специализированных | 3 базовых + 3 специализированных, последние — условно |
| Страна | выводится из телефонного префикса | настоящая колонка `customers.country` |
| Фильтр выручки | только `completed` + `shipped` | всё, кроме `cancelled`, и это переключаемо агентом |
| Нет базы при старте | сервер падает | сервер стартует и отвечает `CONFIGURATION_ERROR` |
| Docker | вынесен из scope | сделан и проверен живым клиентом |

Оба варианта решают одну задачу; разница в том, кому доверено решение. Здесь сервер
старается не решать за агента (отсюда `include_cancelled`, `rank_by` и обе метрики на каждой
строке товара) и вместо этого делает границы данных видимыми.
